# 0010: Data model and consistency rules

**Context.** Phase 1 defines the schema every later phase builds on. Mistakes here are expensive to undo on a live
database, so the rules are written down.

**Decisions.**

- **Identifiers:** UUIDv7 (`@default(uuid(7))`, native `uuid` type). Time-ordered, so B-tree indexes stay compact and
  ids sort by creation time. Rows inserted with raw SQL use `uuidv7()` from `packages/core`.
- **Time:** every column is `timestamptz(3)`, and every database session must run in UTC. Prisma's pg adapter sends
  timestamps as UTC wall-clock time without an offset, which Postgres reads in the _session_ time zone: on a non-UTC
  server (e.g. a developer machine in Asia/Calcutta) every instant was stored shifted by the offset. The
  `utc_timezone` migration sets the database default to UTC (a no-op on Supabase and CI, which already use UTC), and the
  API and worker refuse to start on a non-UTC session (`assertUtcSession`). A per-connection `SET TIME ZONE` was
  rejected: it races the first query (deprecated in pg 9), and startup `options` are not reliably passed through
  Supabase's pooler. Regression tests: `packages/db/test/timezone.int.test.ts`.
- **Tenancy:** `Organization → Project`. Every job-domain row carries `projectId`; membership and roles live on
  `Membership`. Isolation is enforced in the service layer and tested in Phase 2.
- **Job status changes** go through `transitionJob()` only: one `UPDATE … WHERE status IN (allowed) [AND version = n]`
  that also increments `version`. The state machine (`packages/shared/src/domain/status.ts`) decides which moves exist;
  the database decides who wins a race. No read-then-write.
- **History is append-only:** `JobAttempt` and `JobEvent` rows are never rewritten after they finish; retries and
  replays add rows. Replays are new `Job` rows linked by `replayOfId`.
- **Payloads** live in `JobPayload` (1:1), never in list queries; `sha256` of canonical JSON detects conflicting
  re-registrations.
- **Transactional outbox:** queue work is written as `OutboxMessage` rows inside the business transaction and moved to
  BullMQ by `dispatchOutboxBatch()` (`FOR UPDATE SKIP LOCKED`, safe with many dispatchers). The `dedupeKey` is the BullMQ
  job id, so delivery is at-least-once and duplicates collapse.
- **Idempotency keys** reserve the key (`IN_PROGRESS`) before work starts; concurrent duplicates get 409, completed ones
  replay the stored response, and abandoned reservations are taken over after 60 s.
- **Quotas** are consumed with a single conditional upsert, so concurrent requests cannot exceed the limit.
- **Worker heartbeats** live in Redis (sorted set `dl:workers`), not Postgres, to avoid a write every few seconds.
- **Naming:** Prisma's default camelCase identifiers (raw SQL quotes them). Chosen over `@map` snake_case to keep the
  schema readable; consistent everywhere.
- **Migrations** are forward-only and generated by `prisma migrate dev`. Destructive changes ship in a later release than
  the code that stops using a column. They run in CI before integration tests, and on Render at container start
  (`packages/db/scripts/migrate.mjs`, TLS-verified against `DATABASE_CA_CERT` when set).

**Consequences.** Every write path must use the service functions in `packages/core`; direct `prisma.job.update` calls
that change `status` are a review blocker.
